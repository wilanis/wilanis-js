# L009

- **Family:** L -- layers, effects and visibility
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/atomic.ts`
- **Proved by:** `packages/runtime/test/sabotage-atomic.test.ts` (`is refused where it reaches an effect that cannot
  take part -- L009`), `packages/runtime/test/sabotage-served.test.ts` (`L009 once, under the profile that serves the
  route running the atomic graph`)

## Refuses when

A graph marked `"atomic": true` reaches, under some profile that runs it, an effect whose operation is not
transactional: one that cannot commit or roll back with the rest, such as an HTTP request or a file parse. The walk
follows the graph's nodes, the domain operations they run, each profile's binding of those, and the graphs those
reach, so the effect may sit several documents down. The refusal is made in the file and at the node where the effect
runs (`nodes/<id>`), and names the atomic graph whose promise cannot be kept and the profiles that reach the effect;
one fault is one refusal, however many profiles find it.

A profile runs the graph when the binding it chooses lists the graph behind an operation something the profile serves
reaches: a trigger its startup serves (A006 says which), a policy such a trigger attaches, a startup step or a port a
plugin requires. A graph only routes reach is not judged under a profile that never listens. One behind an operation
nothing reaches at all is judged wherever its binding is chosen.

## Example

Mark the customers `import-customers` domain graph atomic; it parses a CSV and, under the live profile, registers
over HTTP. `production-scheduler` and `production-worker` bind what `production` binds, but only the import route runs
the graph and neither opens a route, so neither is named:

```
L009  @features/customers/data/parse-drafts.graph.json#nodes/drafts
    atomic graph '@features/customers/domain/import-customers.graph.json' reaches '@blob/csv.port.json#parse', which cannot take part in a transaction (profiles 'live', 'local', 'production')
    → read or send that outside the transaction: in the caller for a domain graph, in a graph of its own for a data graph
L009  @features/customers/data/create-row.graph.json#nodes/posted
    atomic graph '@features/customers/domain/import-customers.graph.json' reaches '@http/http.port.json#request', which cannot take part in a transaction (profile 'live')
    → read or send that outside the transaction: in the caller for a domain graph, in a graph of its own for a data graph
```

## Fix

Split the graph so the transaction holds only what can roll back: read or send the rest before or after it, in the
caller for a domain graph, or in a graph of its own for a data graph. Where only one profile's binding reaches the
effect, as `live` does above, the fix may be that binding: meet the operation under that profile with a store that
takes part. If nothing was meant to be one transaction, delete `atomic`.
