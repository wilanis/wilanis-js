# A002

- **Family:** A -- access
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/access.ts`
- **Proved by:** `libraries/access/test/access.test.ts` (`A002 a reason the decision can reach that outcomes does not map, and a challenge without a method`)

## Refuses when

A policy's `outcomes` does not say what a refusal of its decision means. Three forms: a reason the decision can refuse
with, under any profile, has no entry in `outcomes` (at `outcomes`, naming the document that refuses); an outcome
whose effect is `challenge` names no `method`, so the guard would not know what to open (at `outcomes/<reason>`); or
an outcome whose effect is `deny` names a `method`, which means nothing there (at `outcomes/<reason>/method`).

## Example

Delete `forbidden` from `employees-only`'s outcomes while the graph behind it still refuses with it:

```
A002  @features/access/edge/employees-only.policy.json#outcomes
    @features/access/domain/require-employee.graph.json may refuse with reason 'forbidden', which outcomes does not map
    → add "forbidden": { "effect": "deny" } or { "effect": "challenge", "method": "..." }
```

Drop the method from `otp-verified`'s challenge instead:

```
A002  @features/access/edge/otp-verified.policy.json#outcomes/otp
    outcome 'otp' challenges but names no method
    → name the method the guard opens: "method": "otp"
```

## Fix

Map every reason the decision reaches to `deny`, or to `challenge` with the method the guard opens (one the guard
declares; X102 judges that). Take `method` off a `deny`, or make it a challenge.
