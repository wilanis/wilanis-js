# X405

- **Family:** X -- plugin rules, @queue (@wilanis/plugin-queue)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-queue/src/rules.ts`
- **Proved by:** `packages/plugin-queue/test/rules.test.ts` (`X405: a publish in an atomic graph to a broker outside the store`, from `a broker whose kind is not marked storage` to `a profile that stands a broker outside the store in for the one inside it`)

## Refuses when

A graph marked `atomic` has a node that runs `@queue/queue.port.json#publish` whose `connection` is of a kind not
marked `storage`, under the tree or under any profile. `publish` is `transactional`: where the broker keeps its
queue in the store, the message joins the graph's transaction and exists exactly when the graph's writes commit.
A broker outside the store has no part in that transaction, so a message it kept would outlive the rollback of the
writes it announces, and a consumer would act on work that never happened. The refusal sits at
`nodes/<id>/in/connection` and names the connection, its kind and, where a stand-in is the cause, the profile.

The rule sees the graph that carries the node. An atomic graph that reaches such a publish through a domain call is
refused when it runs: the handler fails the node with `'<connection>' cannot take part in a transaction: publish
after the atomic graph` before the broker keeps anything.

## Example

Mark the graph that publishes removals `atomic` while its broker is an in-process queue:

```
X405  @features/customers/data/publish-removal.graph.json#nodes/published/in/connection
    an atomic graph publishes to '@connections/jobs.connection.json', of kind '@queue-memory/memory.connection-kind.json', which is not marked storage: a broker outside the store cannot join the graph's transaction, so the message would outlive a rollback
    → publish after the atomic graph, in its caller, reached by a data dependency on its answer
```

## Fix

Move the `publish` out of the atomic graph and into its caller, on a node that reads the atomic graph's answer: the
data dependency means it runs only once the transaction has committed, and never after a rollback. Or, where the
queue should move with the writes, publish to a connection whose kind is marked `storage` -- the storage engine's
own, where the queue is a table beside the records -- and the message joins the transaction.
