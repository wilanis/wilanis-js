# B010

- **Family:** B -- bindings, profiles and startup
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/required.ts`
- **Proved by:** `packages/runtime/test/required-binding.test.ts` (`B010 when what it reaches holds something past the run`, `B010 when what it reaches refuses on purpose, delegated to or run as a graph`), `packages/runtime/test/sabotage-project.test.ts` (`B009 and B010 a binding of the guard's memory that reads the request, or ends the run on purpose`)

## Refuses when

A plugin fires an operation of a port it requires expecting an answer or a failure. Under each profile the checker
walks what each operation of the port reaches, whether the binding delegates or runs a graph, and refuses what ends
the run on purpose: a `refuse` (`reaches a refuse of '<reason>'`), or an operation marked `holds`, which starts
something that outlives the run. The walk is judged rather than the delegation written, since a graph whose last node
refuses ends the run as surely as a delegation to a refusing operation. The refusal sits on the document where the
refuse or the effect is: at the node's id in a graph, at the operation's name in a binding.

## Example

Have the binding of `@auth/state.port.json` delegate `getSession` to `@http/server.port.json#listen` (L003 comes with
it, since the state feature does not allow that effect). One refusal per profile:

```
B010  @features/state/data/auth-files.binding.json#getSession
    @auth/state.port.json#getSession reaches '@http/server.port.json#listen', which holds something past the run, but @auth fires it expecting an answer or a failure (profile 'live')
    → answer or fail; a required operation never ends the run on purpose
```

## Fix

Bind the operation to something that answers, or fails when it cannot, as the port's `returns` describes. Something
meant to run once and outlive the run belongs in `project.json → startup`.
