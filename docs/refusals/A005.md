# A005

- **Family:** A -- access
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/access.ts`
- **Proved by:** `packages/runtime/test/sabotage-access.test.ts` (`A005 a policy reading the caller on a trigger that gives the guard nothing`)

## Refuses when

A policy attached to a trigger reads something the guard hands (`request.principal`, `request.session`,
`request.challenge`), and no attachment on that trigger gives the guard a credential that yields it. The guard hands
a principal only once it has verified a token, so a policy that decides on the principal of a trigger that passes no
token decides on nothing. Where the project has no guard at all, the refusal is for a read no kind hands and no plugin
identifies callers to supply. It sits at the attachment, `policies/<index>`.

## Example

Attach `employees-only` and `can-register` to the registration route by name alone, with no `in`:

```
A005  @features/customers/edge/register-customer.trigger.json#policies/0
    policy '@features/access/edge/employees-only.policy.json' reads request.principal, which the guard hands once it verified a token, but no attachment on this trigger gives one
    → write { "policy": "@access/edge/employees-only.policy.json", "in": { "token": "{{request.headers.authorization}}" } } -- the read is where this kind hands the credential
```

## Fix

Write the attachment as an object that gives the guard the credential, as the hint spells it; the read in the hint
is where an http route hands a token, and another kind hands it elsewhere (`wilanis describe` on the kind). A trigger
nobody calls as a person, such as a schedule, has no caller to decide on, and a policy about the caller is the wrong
gate for it.
