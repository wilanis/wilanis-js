# G018

- **Family:** G -- graphs
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/attempts.ts`
- **Proved by:** `packages/runtime/test/sabotage-attempts.test.ts` (`G018 a retry over a POST, over a method read rather than written, and over a binding whose graph POSTs`)

## Refuses when

A `retry` repeats a call that is not idempotent where it is made. A call that failed may already have been applied,
so trying it again may apply it twice: a second charge, a second row. Whether a call is idempotent there is
`Judge.idempotentAt`'s answer. An operation that declares `idempotent`, or whose `key` the site gives, is safe; one
that declares neither is not; one whose idempotence turns on an input, as an HTTP request's does on its `method`, is
judged by the literal the site writes, and refused when the site reads the input rather than writing it. The reason
is the message's tail.

On a data graph's node, or a binding's delegation, the message names the operation. On a binding operation that runs
a graph, or that delegates to a domain operation, it names each effect below that is not idempotent: the node that
runs it, its file when that is another graph, and the profiles that reach it when the walk went through a binding. An
atomic graph's transactional effects are not held to this, since a try that fails rolls them back. The refusal sits
at `nodes/<id>/retry` or `operations/<name>/retry`.

## Example

Retry `create-row`'s POST, and then the REST binding's `submit`, whose domain graph reaches that POST under `live`:

```
G018  @features/customers/data/create-row.graph.json#nodes/posted/retry
    retry over '@http/http.port.json#request', which is not idempotent here: method is "POST"
    → a call that failed may have been applied; drop retry, or reach an operation that is idempotent or carries a key
G018  @features/customers/data/customers-rest.binding.json#operations/submit/retry
    retry over '@features/customers/domain/register-customer.graph.json', whose 'posted' in @features/customers/data/create-row.graph.json runs '@http/http.port.json#request', which is not idempotent here: method is "POST" (profile 'live')
    → a call that failed may have been applied; drop retry, or reach an operation that is idempotent or carries a key
```

## Fix

Drop the `retry`, or make what it repeats safe to repeat: reach an operation that declares `idempotent`, or give the
`key` the operation declares so a second try is known for the first. Where the reason is an input read rather than
written (`method is read from {{in.tier}}; write it as a literal`), write the literal so the call can be judged. Where
the effects below a binding operation should commit together, mark that graph `atomic` and retry the operation that
runs it.
