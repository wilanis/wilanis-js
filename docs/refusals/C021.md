# C021

- **Family:** C -- connections, settings and stores
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/permits.ts`
- **Proved by:** `packages/runtime/test/sabotage-permits.test.ts` (`C021 an operation production reaches and no entry
  permits, naming the trigger, the binding and the feature`, `C021 a connection an included feature reaches, whose
  first repair is leaving the feature out`, `C021 production refuses the new connection the feature allows itself;
  L003 does not`, `C021 and C022 for an inherited list, at the child's extends, naming the parent and how to replace
  it`, `a shared target: the inherited entry permits the stand-in, and its own connection the child still reaches`)

## Refuses when

A profile writes `permits`, and what the tree reaches under that profile holds an operation or a connection no entry
permits (RFC 0016). What a profile reaches is derived, never written: every effectful native operation behind the
bindings the profile chooses, from every trigger, every policy a trigger attaches, every port a plugin requires, and
every startup step that runs under it, and the connections those operations name, a stand-in in place of what it
stands in for (`reachOf`, RFC 0013). An operation is permitted by an entry that is the operation or its port; a
connection by an entry that names it.

A profile that names another under `extends` and writes no `permits` has the parent's list, and is held to it as to
a list of its own (RFC 0043). An inherited entry that names what the parent reaches for a connection the child stands
in for permits the child's stand-in too, so a child that only swaps a connection reaches nothing its parent's list
does not cover. The entry still permits its own connection wherever the child reaches that connection another way.

The message names what is reached, the first root found that reaches it (a trigger, a policy, a startup step by what
it runs, or the port operation a plugin requires) with how many more do, the binding it is reached through, and the
feature the root sits in, with the package it was included from when it was. One refusal is made per operation and
per connection, at `profiles/<name>/permits`. A profile without `permits` permits everything and is never judged.

`feature.json → effects` is what a feature allows its data layer, the same under every profile (L003); `permits` is
what a place allows the whole tree. A feature that lists a new effect for itself passes L003 and is still refused
here, by the profile whose author did not say the place may.

## Example

Leave `@blob/csv.port.json` out of the `production` profile's `permits`, while the customers' export still writes
CSV:

```
C021  @project.json#profiles/production/permits
    profile 'production' does not permit '@blob/csv.port.json#write', reached from
    @features/customers/edge/export-customers.trigger.json through
    @features/customers/data/customers-postgres.binding.json (feature customers)
    → remove the node that reaches it, or bind the port to a binding that does not; else, if production may, add
      "@blob/csv.port.json#write" to profiles/production/permits
```

For a root in an included feature the message ends `(feature access, included from @wilanis/access)`, and the
hint's first clause reads `remove the feature from includes[].features`: an included feature is a unit, and a host
that will not permit what one of its triggers reaches leaves the feature out.

Where the list is inherited, the child writes no `permits` to point at, so the refusal points at
`profiles/<child>/extends`. The message ends `(permits inherited from '<parent>')`, and the hint's last clause says
to write a list of the child's own rather than add an entry. Make `production-worker` extend `production` and write no
`permits`, while the worker works the queue `production` never consumes:

```
C021  @project.json#profiles/production-worker/extends
    profile 'production-worker' does not permit '@queue/worker.port.json#consume', reached from the startup step
    running @queue/worker.port.json#consume (permits inherited from 'production')
    → remove the node that reaches it, or bind the port to a binding that does not; else, if production-worker may,
      write profiles/production-worker/permits: a list it writes replaces production's whole
```

## Fix

Remove the reach first: the node that runs the operation or names the connection, or, where another binding of the
port does not reach it, choose that binding under the profile. Only when the place may do it, add the entry the hint
writes to `profiles/<name>/permits`; that line under the profile's name is the diff a reviewer reads. For an
inherited list, write the child's own `permits`: a list it writes replaces the parent's whole, so it lists everything
the child may reach, not only what the parent's list lacks.
