# B011

- **Family:** B -- bindings, profiles and startup
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/profiles.ts`
- **Proved by:** `packages/runtime/test/sabotage-promise.test.ts` (`B011 a domain operation promising idempotent whose binding under a profile POSTs`)

## Refuses when

A domain operation marked `idempotent: true` promises that calling it twice does what calling it once does. The
promise is the port's and the effects are the binding's, so under each profile the checker follows the binding that
meets the port there, through any domain graph and the bindings it calls, to every effect it reaches, and refuses each
effect that is not idempotent where it is made: an HTTP `POST`, or a store operation that declares neither
`idempotent` nor a `key`. The refusal sits on the port at `operations/<name>/idempotent` and names the profile, the
binding, the node and its graph, the operation the node runs, and why it is not idempotent there.

## Example

Mark the customer port's `register` idempotent. Under `live` its binding POSTs:

```
B011  @features/customers/domain/customer.port.json#operations/register/idempotent
    '@features/customers/domain/customer.port.json#register' promises idempotent, but @features/customers/data/customers-rest.binding.json (profile 'live') reaches 'posted' in @features/customers/data/create-row.graph.json, which runs '@http/http.port.json#request', not idempotent here: method is "POST"
    → drop idempotent, or bind the operation under that profile to a graph whose effects are idempotent or keyed
```

Under `local` and `production` it is refused three times each, once per store effect its graph reaches that declares
neither `idempotent` nor a `key`.

## Fix

If the operation is not idempotent, drop the promise. If it should be, bind it, under each profile the refusals name,
to a graph whose effects are idempotent where they are made, or keyed so that a repeat lands on the same record.
