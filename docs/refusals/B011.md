# B011

- **Family:** B -- bindings, profiles and startup
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/profiles.ts`
- **Proved by:** `packages/runtime/test/sabotage-promise.test.ts` (`B011 a domain operation promising idempotent whose binding under a profile POSTs`,
  `B011 refuses a promise whose graph asks newKey for the key, though the puts beside it are idempotent`),
  `packages/runtime/test/sabotage-served.test.ts` (`B011 once, under the profile that serves the routes reaching the
  operation`)

## Refuses when

A domain operation marked `idempotent: true` promises that calling it twice does what calling it once does. The
promise is the port's and the effects are the binding's, so under each profile the checker follows the binding that
meets the port there, through any domain graph and the bindings it calls, to every effect it reaches, and refuses each
effect that is not idempotent where it is made: an HTTP `POST`, or an operation that declares neither `idempotent`
nor a `key`, as the store's `newKey` does. The refusal sits on the port at `operations/<name>/idempotent` and names the profile, the
binding, the node and its graph, the operation the node runs, and why it is not idempotent there.

An operation is not held to its promise under a profile where only triggers that profile does not serve reach it, as
a route under a profile whose startup never listens (A006 says which profile serves which trigger): nothing that
profile runs calls it. One a served trigger, a policy it attaches, a startup step that runs there or a plugin's
requirement reaches is held there, and so is one nothing reaches at all.

## Example

Mark the customer port's `register` idempotent. Under `live` its binding POSTs:

```
B011  @features/customers/domain/customer.port.json#operations/register/idempotent
    '@features/customers/domain/customer.port.json#register' promises idempotent, but @features/customers/data/customers-rest.binding.json (profile 'live') reaches 'posted' in @features/customers/data/create-row.graph.json, which runs '@http/http.port.json#request', not idempotent here: method is "POST"
    → drop idempotent, or bind the operation under that profile to a graph whose effects are idempotent or keyed
```

Under `local` and `production` it is not refused: its graph there writes two `put`s, which the store declares
idempotent. Mark `submit` idempotent instead and it is refused under those two as well, once each, because its
domain graph asks `nextId` for the key before it registers, and a key `newKey` makes fresh on every call is what a
repeat would write a second customer under:

```
B011  @features/customers/domain/customer.port.json#operations/submit/idempotent
    '@features/customers/domain/customer.port.json#submit' promises idempotent, but @features/customers/data/customers-store.binding.json (profile 'local') reaches 'key' in @features/customers/data/next-id.graph.json through '@features/customers/domain/customer.port.json#nextId', which runs '@storage/store.port.json#newKey', not idempotent here: '@storage/store.port.json#newKey' declares neither idempotent nor key
    → drop idempotent, or bind the operation under that profile to a graph whose effects are idempotent or keyed
```

`production-scheduler` and `production-worker` bind both as `production` does, but only routes reach them and
neither profile listens, so neither is named.

## Fix

If the operation is not idempotent, drop the promise. If it should be, bind it, under each profile the refusals name,
to a graph whose effects are idempotent where they are made, or keyed so that a repeat lands on the same record.
