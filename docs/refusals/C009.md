# C009

- **Family:** C -- connections, settings and stores
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/contracts.ts`
- **Proved by:** `packages/runtime/test/sabotage-atomic.test.ts` (`is refused where it says nowhere static to resolve a connection from -- C009`),
  `packages/runtime/test/sabotage-names.test.ts` (`C009 a transactional operation that marks no field names, beside the
  C025 for the unmarked store`, `C009 a transactional operation that marks two fields names: its transaction would fall
  on two`)

## Refuses when

A port operation marked `transactional` does not mark exactly one field it accepts `"names": "connection"` or
`"names": "store"`. An atomic graph's one transaction is judged before anything runs, by following the connection
each effect goes to, and the compiler follows the one marked field: a connection document, or a store that names
one. With no marked field there is nothing to follow; with two, one call would fall on two connections. That the
field is static and a string is [C025](C025.md)'s. It points at `operations/<name>/accepts` of the port, which in
practice is a plugin's.

## Example

A plugin shipping a transactional operation that accepts only a string:

```
C009  @fake/fake.port.json#operations/write/accepts
    operation 'write' is transactional but marks no field "names": its transaction falls on what one field names
    → mark the one field the transaction falls on "names": "connection" or "names": "store", static
```

## Fix

In the port, mark the one field the transaction falls on `"names": "connection"` or `"names": "store"`, with
`"static": true`, as the hint says; where two are marked, keep the mark on that one alone. If the operation cannot
say where it writes before it runs, it cannot take part in a transaction: drop `transactional`.

## History

- 0.1.0: introduced.
- 0.1.0: restated over the mark, not the name: the one field marked `names`, where it was a static field called
  `connection` or `store` (RFC 0037).
