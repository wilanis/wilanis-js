# X233

- **Family:** X -- plugin rules, @storage-sqlite (@wilanis/plugin-storage-sqlite)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-storage-sqlite/src/rules.ts`
- **Proved by:** `packages/plugin-storage-sqlite/test/rules.test.ts` (`X233 a collection name SQLite keeps for its own`, `X233 two collections of one connection that fold to one table name`)

## Refuses when

A collection kept over a sqlite connection has a name SQLite will not create as a table, or one it will not keep
apart from another collection of the same connection. The refusal sits at `collections/<name>`, in two forms:

- the name is not a letter or an underscore followed by letters, digits or underscores, or it begins with
  `sqlite_` in any case, which SQLite keeps for its own tables and refuses at `CREATE TABLE`;
- the name folds to the same lower-case name as a collection seen before it on the same connection. SQLite compares
  identifiers without case, so `entriesKept` and `entrieskept` are one table, and the engine's `named` answers the
  same fold. The later of the two is refused.

Two stores that declare one name with different shapes are @storage's to refuse (X207); this rule refuses what only
the fold makes one.

## Example

Declare `entriesKept` and `entrieskept` in the customers store, over a sqlite connection:

```
X233  @features/customers/data/customers.store.json#collections/entrieskept
    'entrieskept' and 'entriesKept' are one table once folded to lower case, and SQLite compares names without case
    → rename one of the two collections
```

A name that is not a table name reads `'<name>' is not a table name this engine can create: a letter or an
underscore, then letters, digits or underscores, and not beginning with sqlite_, which SQLite keeps for its own`,
with the hint `rename the collection`.

## Fix

Rename the collection, or one of the two that fold together, to a name that is legal and distinct once lower-cased.
Every graph and binding that names the collection must follow the rename. A collection that already holds rows
keeps them only if it records its old name under `was`, so a migration renames the table rather than dropping it;
this engine applies a migration plan once RFC 0022's sixth step lands.
