# X213

- **Family:** X -- plugin rules, @storage (@wilanis/plugin-storage)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-storage/src/rules.ts`
- **Proved by:** `packages/runtime/test/sabotage-storage.test.ts` (`X213 a graph of one feature naming another feature's store`)

## Refuses when

A call to a `@storage` operation, from a data graph or a binding, names a store that lives in another feature. A
collection is a detail of the feature that declares it; another feature reaches those records through the owning
feature's domain port. A store is never in `exports`, so L005 cannot say this, and the plugin does. The refusal sits
at `.../in/store`.

## Example

Plant a data graph in the hello feature that reads a customer out of the customers store:

```
X213  @features/hello/data/peek.graph.json#nodes/peeked/in/store
    '@features/customers/data/customers.store.json' is customers's store, and this is hello
    → reach another feature's records through its domain port
```

## Fix

Call the operation of the owning feature's domain port that answers the records (here
`@customers/domain/customer.port.json#get`, from a domain graph, with the port in that feature's `exports` and the
feature in `dependsOn`). If the records belong to this feature, move the store into it.
