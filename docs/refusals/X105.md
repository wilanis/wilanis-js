# X105

- **Family:** X -- plugin rules, @auth (@wilanis/plugin-auth)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-auth/src/rules.ts`
- **Proved by:** `packages/runtime/test/sabotage-scoping.test.ts` (`X105 a set that writes the tenant, naming the store that scopes customers by it`), `packages/plugin-auth/test/attributes.test.ts` (`a set that writes the attribute a store scopes by is refused, naming the store and the collection`)

## Refuses when

A `@auth/session.port.json#set` writes, or a `#remove` drops, a session attribute that some store scopes a collection
by, from a graph's node or a binding's operation. A scoped collection keeps each row under the value its scope reads
from `request.session.attributes`, and that value is what the sign-in graph gave `@auth/token.port.json#issue`. A
later write would move the caller, and the rows they reach, into another scope, which is what scoping forbids. The
refusal sits at `.../in/values/<key>` for a set and `.../in/keys` for a remove, and names the store and the collection.

## Example

Have the access tree's theme write set the tenant as well, which both of the example's customer stores scope by:

```
X105  @features/access/data/write-theme.graph.json#nodes/written/in/values/tenant
    set writes 'tenant', which @features/customers/data/customers-postgres.store.json scopes customers by; a scope is written at sign-in and never again
    → drop it: a scoped attribute is what the sign-in graph gave token.port.json#issue, and only that
```

## Fix

Drop the attribute from the write. A caller whose scope must change signs in again, and the sign-in graph issues the
token with the new value. If the attribute was never meant to scope anything, the store's `scoped` column is what to
change, not the write.
