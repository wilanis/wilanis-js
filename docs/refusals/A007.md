# A007

- **Family:** A -- access
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/scope-access.ts`
- **Proved by:** `packages/runtime/test/sabotage-scope-access.test.ts` (`A007 a scope read from a header or a route parameter`)

## Refuses when

A store scopes a collection by a read that the guard does not hand. A scope decides whose rows a caller sees, so what
fills it must be what the guard established about the caller before any graph ran; a header, a route parameter or a
query string is the caller's own word for who they are, and a store scoped by one is scoped by nothing. The judgement
is over the store document, since after lowering a resolver read and a hand-written request read are the same source.
Where the project has no guarding plugin, a store that scopes anything is refused once, since there is nobody for a
scope to be the scope of. The refusal sits at the store's `reads/<name>`, the line an author would change.

## Example

Point the `tenant` resolver the customer stores scope by at a header:

```
A007  @features/customers/data/customers.store.json#reads/tenant
    scopes customers, and reads request.headers.x-tenant: a caller may send any value there
    → a scope reads what the guard hands once it identified the caller (request.principal, request.session, request.challenge); wilanis describe @auth/plugin.json
```

Remove `@auth` from the project instead, and the message reads `'tenant' scopes customers, but no plugin of this
project identifies callers`, with the hint `add a guarding plugin to project.json → plugins, such as
@wilanis/plugin-auth`.

## Fix

Scope by what the guard hands once it has identified the caller, such as `request.session.attributes.tenant` or
`request.principal.subject`; `wilanis describe` on the guard's `plugin.json` lists its context. A tree that scopes its
stores needs a guard to identify who each scope belongs to.
