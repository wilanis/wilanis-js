# X224

- **Family:** X -- plugin rules, @storage-postgres (@wilanis/plugin-storage-postgres)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-storage-postgres/src/rules.ts`
- **Proved by:** `packages/plugin-storage-postgres/test/rules.test.ts` (`X224 a queueVisibility longer than a Node
  timer can wait: a running delivery renews its lock every half of it, on a timer`)

## Refuses when

The plugin's `queueVisibility` setting, in seconds, is above 4294967 (about 49.7 days). While a run goes on, its
worker extends the message's lock every half window (`renewal.ts`), and that wait is a Node timer. Node fires a timer
set above 2147483647 ms (2^31 - 1, about 24.8 days) after 1 ms, so with a longer window every running delivery would
renew its lock without pause. The bound is the longest whole number of seconds whose half a timer can wait. The
refusal sits in `@project.json` at `plugins/@storage-postgres/settings/queueVisibility`.

## Example

Set a visibility window of 60 days:

```
X224  @project.json#plugins/@storage-postgres/settings/queueVisibility
    queueVisibility is 5184000; it is how many seconds a dead worker keeps its message, a running one renews its lock every half of it, and a Node timer waits at most 2147483647 ms (about 24.8 days): a longer one fires after 1 ms, so every running delivery would renew its lock without pause
    → set it to 4294967 or less, or drop it for the default of 30
```

## Fix

Write a `queueVisibility` of 4294967 or less, or delete it for the default of 30 seconds. The window only bounds how
long a worker that died keeps its message, so a short one is rarely wrong.
