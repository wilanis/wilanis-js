# S006

- **Family:** S -- scenarios
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/scenarios.ts`
- **Proved by:** `packages/runtime/test/sabotage-shared-answers.test.ts` (`refuses a recorded scenario copied by hand
  with its digests kept, at each node and at sharedStubs`, `refuses one that keeps only sharedStubs, its answers
  inline`, `says which answer it points at, and names --pin first and the edit that writes the value in its place
  second`, `refuses it inside a recorded directory too, though every digest resolves there, and S007 says nothing`);
  the fix it names first, in `packages/runtime/test/scenarios-pin.test.ts`

## Refuses when

A scenario written by hand (one with no `generated` mark) points into an answers document (RFC 0036). Two forms are
refused:

- a node of `expect.nodes` written as a digest instead of an answer. The refusal sits at `expect/nodes/<node>`, one
  per node.
- a `sharedStubs` map, whatever it holds. The refusal sits at `sharedStubs`, once.

An answers document (`answers.json` at the top of a recorded directory) belongs to the command that records there:
`wilanis rehearse --record` or `wilanis fuzz --edges`. That command writes the file whole each time, from the
scenarios it records, and knows nothing of a scenario a person wrote. So a value a hand-written scenario points at
could disappear on the next record. A hand-written scenario holds its answers under `expect.nodes` and its stub values
under `stubs` itself. This holds wherever the scenario sits, a recorded directory included, and whether or not its
digests resolve today. S007 judges only a recorded scenario, so a hand-written one that points gets this refusal
alone.

## Example

```
S006  @scenarios/customers.get-row.outcome.noCustomer.scenario.json#expect/nodes/op.outcome
    node 'op.outcome' points at the shared answer 57a449dbd5d11643, and a scenario written by hand holds its answers itself: no command keeps an answers file for it
    → delete this file, then wilanis scenarios --pin <the recorded file> writes it again with every answer and stub inline; or write the answer answers.json holds under nodes/57a449dbd5d11643 in place of the digest
```

At `sharedStubs` the message is `the scenario shares its stubs under sharedStubs, and a scenario written by hand holds
its stubs itself: no command keeps an answers file for it`, and the hint is `delete this file, then wilanis scenarios
--pin <the recorded file> writes it again with every answer and stub inline; or move each entry of sharedStubs under
stubs, with the value answers.json holds under stubs/<digest>`.

## Fix

Delete the copy, and let `wilanis scenarios --pin` write it. Delete it first: the command line checks the tree before
`--pin` runs, and while the copy is there, `check` refuses it with this code. Name the recorded file, by its path
below the root:

```
$ wilanis scenarios example --pin scenarios/rehearsed/customers.get-customer/customers.get-row.outcome.noCustomer.scenario.json
wrote scenarios/customers.get-row.outcome.noCustomer.scenario.json with every answer and stub inline -- give it a description of your own
```

It writes `scenarios/<the file name>` with every value inline and no `generated` mark, and refuses where that file is
already there. Then say in its description why the run is kept.

Or write every value inline by hand. Replace each digest under `expect.nodes` with the answer the recorded directory's
`answers.json` holds under it (`nodes/<digest>`). Move each entry of `sharedStubs` under `stubs`, with the value
`answers.json` holds under `stubs/<digest>`, and delete `sharedStubs`.

If the file is a recorded scenario that lost its `generated` mark, put the mark back instead.
