# C022

- **Family:** C -- connections, settings and stores
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/permits.ts`
- **Proved by:** `packages/runtime/test/sabotage-permits.test.ts` (`C022 an operation, a port or a connection
  production permits and does not reach`, `live's list on production: the reach is per profile, and a stand-in is
  what is reached`, `C021 and C022 for an inherited list, at the child's extends, naming the parent and how to replace
  it`, `a shared target the child no longer reaches its own way: the entry still permits the stand-in, no C022`,
  `C022 an inherited entry the child reaches neither as written nor through its stand-in`)

## Refuses when

An entry of a profile's `permits` permits nothing the profile reaches (RFC 0016): an operation entry the reach does
not hold, a port entry none of whose operations it holds, or a connection entry no reached operation names. The
list is held to the reach in both directions, so it never stays wider than the tree once a node is removed: a list
that may be wider tells a reviewer what the tree might do, not what it does. The refusal points at the entry.

What is reached is per profile. A startup step that runs under other profiles alone is not reached here, and an
entry for what it runs is refused.

A profile that names another under `extends` and writes no `permits` has the parent's list, and each entry is held to
the child's reach as strictly as an entry of its own (RFC 0043). An inherited entry that names what the parent reaches
for a connection the child stands in for permits the child's stand-in as well as its own connection, so it is refused
only where the child reaches neither. The child writes no `permits` to point at, so the refusal points at
`profiles/<child>/extends`, and its message says `inherits '<entry>' from '<parent>'` where an entry of its own says
`permits '<entry>'`.

## Example

Add `@reload/watch.port.json#watch` to the `production` profile's `permits`, though the step that runs it names
`live` and `local` alone:

```
C022  @project.json#profiles/production/permits/13
    profile 'production' permits '@reload/watch.port.json#watch', but nothing it reaches runs it
    → remove it from profiles/production/permits
```

Make `production-worker` extend `production` and write no `permits`. The worker never listens, so the inherited entry
for the listener permits nothing it reaches:

```
C022  @project.json#profiles/production-worker/extends
    profile 'production-worker' inherits '@http/server.port.json#listen' from 'production', but nothing it reaches
    runs it
    → write profiles/production-worker/permits: a list it writes replaces production's whole
```

Where the inherited entry carries a stand-in, the message names it too. Make `production-scheduler` extend
`production`, write no `permits`, and stand `employees-staging.connection.json` in for `employees.connection.json`.
The scheduler verifies no one, so it reaches neither the connection `production` names nor the stand-in:

```
C022  @project.json#profiles/production-scheduler/extends
    profile 'production-scheduler' inherits '@connections/employees-production.connection.json' from 'production',
    but no operation it reaches names that connection, nor '@connections/employees-staging.connection.json', which
    this profile reaches in its place
    → write profiles/production-scheduler/permits: a list it writes replaces production's whole
```

## Fix

Remove the entry. If the profile should reach it, the fix is in what it reaches (a startup step's `profiles`, the
binding the profile chooses), and the entry then stops being refused. For an inherited entry there is no line of the
child's to remove: write the child's own `permits`, which replaces the parent's list whole, and leave the entry out
of it.
