# X234

- **Family:** X -- plugin rules, @storage-sqlite (@wilanis/plugin-storage-sqlite)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-storage-sqlite/src/rules.ts`
- **Proved by:** `packages/plugin-storage-sqlite/test/rules.test.ts` (`X234 a busyTimeoutMs longer than a Node timer
  can wait: a writer of this process waits its turn on a timer`)

## Refuses when

The plugin's `busyTimeoutMs` setting, rounded to whole milliseconds as the engine reads it, is above 2147483647
(2^31 - 1 ms, about 24.8 days). A writer of this process waits its turn on the file on a Node timer (`turns.ts`),
and Node fires a timer set longer than that after 1 ms. So a writer that has to wait would fail with `database is
locked` at once. The refusal sits in `@project.json` at `plugins/@storage-sqlite/settings/busyTimeoutMs`.

## Example

Let a writer wait 30 days for the file:

```
X234  @project.json#plugins/@storage-sqlite/settings/busyTimeoutMs
    busyTimeoutMs is 2592000000; it is how long a writer waits for the file, in milliseconds, and a Node timer waits at most 2147483647 ms (about 24.8 days): a longer one fires after 1 ms, so a writer that has to wait would fail with 'database is locked' at once
    → set it to 2147483647 or less, or drop it for the default of 5000
```

## Fix

Write a `busyTimeoutMs` of 2147483647 or less, or delete it for the default of 5000. A writer of another process
waits on SQLite's busy handler, which holds the process, so a long wait is rarely what a tree wants.
