# C018

- **Family:** C -- connections, settings and stores
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/profiles.ts`
- **Proved by:** `packages/runtime/test/sabotage-profiles.test.ts` (`C018 a connection standing in for itself, or for one of another kind; R001 one that names nothing`) and `packages/runtime/test/sabotage-broker-profile.test.ts` (a broker standing in for a connection that delivers nothing, or delivers otherwise)

## Refuses when

A profile's `connections` maps a connection the documents name to another that stands in for it under that profile,
and the mapping is no stand-in: the connection is mapped to itself, or to a connection of a different kind. A
connection's kind is a fact about the connection, and every binding and graph that reaches it was checked against
that kind; reaching a system of another kind takes other operations, which is a different binding, not a different
connection. The refusal points at `profiles/<name>/connections`. A connection on either side that the tree does not
have is R001.

A broker is the one exception. Where both kinds declare `delivery` (RFC 0009) and declare the same value, the
stand-in is admitted: what was judged of a connection a queue trigger receives from or a graph publishes to reads
its kind's `delivery`, which the two share, or its `storage` marker, which a stand-in marked `storage` can only
relax. So a profile may swap the in-process broker for the table one, as it swaps one storage engine's connection
for another's. A broker mapped to a connection that delivers nothing, or delivers otherwise (`at-most-once` for
`at-least-once`), is still refused, and the message says what each delivers.

## Example

Map the employees connection to itself under `production`:

```
C018  @project.json#profiles/production/connections
    profile 'production' maps '@connections/employees.connection.json' to itself
    → a stand-in is another connection of kind '@auth/directory.connection-kind.json'; to reach a different kind, bind the port to another binding
```

Mapped to a connection of another kind, the message names both: `profile 'production' maps
'@connections/employees.connection.json', of kind '@auth/directory.connection-kind.json', to
'@connections/customers-api.connection.json', of kind '@http/http.connection-kind.json'`.

Mapped from a broker to a connection that delivers nothing, the message says so: `profile 'production' maps
'@connections/jobs.connection.json', of kind '@queue-memory/memory.connection-kind.json', to
'@connections/customers-api.connection.json', of kind '@http/http.connection-kind.json' (which delivers nothing,
where the other delivers at-least-once)`.

## Fix

Name another connection of the same kind as the stand-in -- or, for a broker, one of any kind that declares the
same `delivery` -- or drop the entry if the profile should reach the connection itself. If the profile should reach a system of another kind, leave `connections` alone and choose, under
the profile's `bindings`, a binding of the port written against that kind.

## History

- 0.1.0: introduced.
- 0.1.0, RFC 0009 step 10: a stand-in of another kind is admitted where both kinds declare the same `delivery`, so a
  profile can move a queue from one broker to another.
