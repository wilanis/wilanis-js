# X222

- **Family:** X -- plugin rules, @storage-postgres (@wilanis/plugin-storage-postgres)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-storage-postgres/src/rules.ts`
- **Proved by:** `packages/plugin-storage-postgres/test/rules.test.ts` (`X222 a key this engine cannot key by`, `X222 a key the configured keyType cannot answer`, `X222 identity over a string key, which counts nothing`)

## Refuses when

A collection kept over a postgres connection is keyed by a field this engine cannot key by, or cannot generate a key
for under the plugin's `keyType` setting. Three forms, all at `collections/<name>/key`:

- the key field is neither a string nor a number (`'id' is boolean, and this engine keys by a string or a number`);
- `keyType` is `identity`, which counts one past the highest key, and the key is a string (`keyType 'identity'
  counts, and 'id' is a string`);
- `keyType` is `uuidv7`, or absent and so `uuidv7`, which answers text, and the key is a number (`keyType 'uuidv7'
  answers text, and 'id' is a number`).

`keyType` says what `newKey` answers for every collection of the tree, so one number-keyed collection and one
string-keyed collection over the same engine cannot both be generated for.

## Example

Make the customer shape's `id` a number, with no `keyType` set on the plugin:

```
X222  @features/customers/data/customers.store.json#collections/entries/key
    keyType 'uuidv7' answers text, and 'id' is a number
    → set the plugin's keyType under project.json, or key the collection by another field
```

## Fix

Where the key type is right, set the plugin's `keyType` in `project.json → plugins` to the one that answers it:
`identity` for a number key, `uuidv7` (or nothing) for a string key. Where the key type is wrong, change the field's
type in the shape, or key the collection by another field. A boolean or structured key has no `keyType` that answers
it, and only the second edit repairs it.
