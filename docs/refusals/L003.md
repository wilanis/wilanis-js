# L003

- **Family:** L -- layers, effects and visibility
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/graph.ts`, `packages/compiler/src/check/bindings.ts`
- **Proved by:** `packages/runtime/test/sabotage.test.ts` (`L003 an effect the feature does not allow`);
  `packages/runtime/test/sabotage-fixes.test.ts` (`L003 offers the effect added to the feature, on every refusal, graph
  node and binding alike`, `L003 applying the first refusal’s fix leaves nothing refused`, `L003 applying all nine adds
  the effect once`)

## Refuses when

A data graph's node runs a native operation that is not `pure`, or a binding's operation delegates to an operation
that is not `pure`, and the feature the document lives in does not list that operation under `feature.json →
effects`. A feature says once which effects it reaches; nothing inside it can widen that. The graph form sits at
`nodes/<id>`, the binding form at `operations/<name>/run`.

## Example

Empty the customers feature's `effects`, and every data graph and binding that reaches an effect is refused, one
refusal per node:

```
L003  @features/customers/data/get-row.graph.json#nodes/fetched
    node 'fetched' runs effectful '@http/http.port.json#request' which the feature does not allow
    → add "@http/http.port.json#request" to @features/customers/feature.json → effects
```

Empty the directories feature's `effects` instead, and its binding is refused at each delegation, at
`@features/directories/data/identity.binding.json#operations/verifyCustomer/run`, saying `'verifyCustomer' delegates
to effectful '@auth/identity.port.json#verify' which the feature does not allow` with a hint of the same form.

## Fix

Add the operation to the feature's `effects`, as the hint spells it, if the feature is meant to reach it. Every
refusal that names the same operation goes with that one edit.

The refusal offers that edit as its one fix, on the graph form and the binding form alike, spelled from the same
source as the hint:

```json
{ "file": "@features/customers/feature.json", "at": "effects", "add": "@http/http.port.json#request" }
```

`add` appends the value to the list at `at` unless it is there already, so applying the fix of every refusal that
names one operation adds it once. `wilanis check` prints only the hint; the fix is on the `Refusal` the checker
answers. The suite applies it to the sabotaged example and holds that the refusals go and none take their place. If the feature is not meant to reach it, the graph is
in the wrong feature, or the effect belongs behind a domain port another feature exports and binds.
