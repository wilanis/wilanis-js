# B005

- **Family:** B -- bindings, profiles and startup
- **Status:** live, since 0.1.0
- **Made in:** `packages/compiler/src/check/bindings.ts`
- **Proved by:** `packages/runtime/test/sabotage-project.test.ts` (`B005 a graph that takes its input whole, bound to an operation that accepts two fields`, `B005 a graph that takes its input whole, fed a field of another type`)

## Refuses when

A bound operation's contract, what the port says it `accepts` and `returns`, must fit what meets it. For a data graph,
at `operations/<name>/graph`: the operation's accepts must be assignable to the graph's `in`; an operation that
accepts fields cannot be met by a graph that takes nothing; a graph whose `in` is not a shape (`string[]`, say) takes
its input whole, so the operation must accept exactly one field, required, of that type; and the graph's `out` must
answer the operation's `returns`, answering nothing where nothing is returned and something where something is. For a
delegation, at `operations/<name>/run`: where the bound operation returns something, the operation delegated to must
return something assignable to it. What a delegation passes as input is judged by the G rules of a call site.

## Example

Add a second field, `reason`, to what the customer port's `removeMany` accepts. The graph that meets it takes a
`string[]` whole, and each of the three bindings is refused:

```
B005  @features/customers/data/customers-rest.binding.json#operations/removeMany/graph
    graph '@customers/domain/remove-customers.graph.json' takes string[] whole, so 'removeMany' must accept exactly one field; it accepts ids, reason
    → a graph whose in is not a shape receives the one field the operation accepts
```

Make `ids` a `number[]` instead:

```
B005  @features/customers/data/customers-rest.binding.json#operations/removeMany/graph
    'removeMany' accepts ids: number[] → graph in string[]: number is not string
    → make 'ids' and the in of graph '@customers/domain/remove-customers.graph.json' one type
```

## Fix

Make the two sides one contract, changing whichever is wrong: the port's `accepts` or `returns`, or the graph's `in`
or `out`. A port is shared by every binding of it and every trigger that fires it, so a change there reaches further
than a change to one graph. A graph that takes its input whole receives the one field the operation accepts; to take
several, give its `in` a shape. For a delegation, `wilanis describe <operation>` shows what it answers.
