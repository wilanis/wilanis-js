# X106

- **Family:** X -- plugin rules, @auth (@wilanis/plugin-auth)
- **Status:** live, since 0.1.0
- **Made in:** `packages/plugin-auth/src/dirs.ts`
- **Proved by:** `packages/runtime/test/sabotage-project.test.ts` (`X106 the guard's memory kept where the loader reads documents, or outside the tree`)

## Refuses when

A binding delegates to `@auth/files.port.json`, which keeps the guard's sessions and challenges as one JSON file per
record, and its `dir` input is relative and would put those files where they do not belong: the tree's root itself,
anywhere above it (`../`), or under `features/` or `connections/`, the directories the loader reads documents from. A
record written there would be read back as a document, or would not be the tree's to keep. An absolute `dir` is taken
as written. The refusal sits on the binding at `operations/<name>/in/dir`, once for each delegation.

## Example

Keep the records under `features/`:

```
X106  @features/state/data/auth-files.binding.json#operations/getSession/in/dir
    'getSession' keeps records in 'features/auth', which is under features/, which the loader reads
    → .wilanis/auth, or an absolute path outside the tree
```

A `dir` of `../auth` says `which is outside the tree`, with the same hint.

## Fix

Write `.wilanis/auth`, or another path under `.wilanis/`, which the loader never reads; or an absolute path outside
the tree, for a process whose state lives elsewhere. Several processes that share sessions want a store behind
`@auth/state.port.json` rather than files.

## History

- 0.1.0: introduced. The rule was numbered X104 for one commit before release and took X106 in 01c8925, so that
  documents still citing X104 for what X103 refuses could not gain a new meaning.
