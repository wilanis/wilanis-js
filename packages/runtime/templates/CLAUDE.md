# Working in this tree

This project is a wilanis tree: behaviour is JSON documents, judged by `wilanis check`, run by a stateless
engine. You do not write handler code. You write documents and the compiler tells you what is wrong, with
the file, the rule and the fix.

## The loop

1. Edit or add documents. After every edit the hook runs `wilanis check`. Read the refusal, fix it, do not work around it.
   `wilanis check --json` gives the same refusals as data. A refusal that carries `fixes` is repaired by applying the
   first fix as written (`set`, `add` or `remove` the value at its `at` in its `file`, or `move` the file); one that
   carries none, by reading its `hint`. After every edit, check again. In one file, fix the first refusal before the
   ones below it, since a later one is often the first one's shadow.
2. Before you stop, `wilanis rehearse` runs every trigger with stubbed effects, and every branch of every `switch` it
   reaches -- each rule solved from its own expression, so no branch is left to chance. Read the last line: it either
   says every branch settled, or lists the problems. `ok` lines are fine, including `refused on purpose`, which is a fail
   node the graph declares. A switch's `catch` is a branch too, `when <node> broke`, walked by making that stubbed
   effect break. The three to fix: `NEVER RUN` is a rule no inputs can reach, `BROKE` is a branch that fails
   where the graph declares no failure, `BLOCKED` is a wiring hole.
3. `wilanis fuzz` writes scenarios under `scenarios/fuzz/`; `wilanis regress` replays them. Run regress after any change
   to a graph or binding. A scenario directly under `scenarios/` with no `generated` and a description ending
   `Generated by wilanis fuzz; edit stubs to pin an edge case.` is one an older `fuzz` wrote and nothing owns now:
   delete it, or move it into `scenarios/fuzz/`.
4. When a contract is unclear: `wilanis describe <path>`. When you need the lay of the land: `wilanis ls`, `wilanis map`.

A Stop hook judges the tree before you may finish: `wilanis check`, then `wilanis rehearse`, then the gate
named as `gate` in `.claude/wilanis.json` where the tree declares one, and anything that refuses blocks the
stop with what refused as the reason. What unblocks it is a tree that checks, rehearses and passes its gate --
nothing else; after five blocks in a row the stop is allowed with the verdict attached, and then your answer
must say the tree does not check and what refused.

## Vocabulary

Every file opens with its `$schema` and a `description`. A `label` (optional, on any document and on any
node) is the short human name a reader sees in the viewer instead of the path or the id; write one when the
file name would not say enough.

Every file opens with its `$schema`. The schema for a kind is

```
https://raw.githubusercontent.com/wilanis/wilanis-js/main/packages/core/schemas/<kind>.schema.json
```

(the alias `@wilanis/<kind>.schema.json` is also accepted). Fetch the schema when a field is unclear: every
property is described.

| kind | what it is | where |
|---|---|---|
| `project` | aliases, plugins (`use`, `from`, `settings` incl. the codecs table), includes (trees whose features load here), secrets, startup (a step's `profiles` names where it runs; absent, everywhere), profiles (`bindings`; `connections`, a stand-in of the same kind per connection; `default`, the one a start that names none runs) | `project.json` |
| `feature` | dependsOn, exports, effects allowlist | `features/<name>/feature.json` |
| `shape` | a named object type; `layer: edge` (the world's) or `core` (ours); a list field may say `maxItems` | `edge/` or `domain/` |
| `port` | a contract: operations with accepts / returns, each maybe `pure`, `refuses`, `holds` or `transactional`; `accepts` is fields by name, or the path of a shape whose fields the operation takes (`"accepts": "@customers/domain/CustomerUpdate.shape.json"`), and a call site gives them one by one either way; a field may be `static`; an operation may say `idempotent` (always, or when an expression over its inputs holds) or name its `key` | `domain/` |
| `binding` | how a port is met -- a domain port, or one a plugin requires: per operation a graph or a delegation (`run` + `in`); an operation may say `timeoutMs` and `retry` | `data/` |
| `graph` | dataflow: nodes of type run / switch / map, `in`, `out.from`, constants; `atomic` when its effects commit or roll back together; a data graph may name `reads`, and a data graph's node may say `timeoutMs` and `retry`; a `map` may say `limit` (the most elements) and `concurrency` (how many at once). A data graph's switch may `catch` a node's fault: `"catch": { "<node>": "<target>" }` routes to the target when that node breaks, and the rules and `else` are not tried; a refusal is never caught. A change to a record is a pair, and `wilanis new graph` writes each half with `TODO` where a value goes: `--port <port> [--read get] [--write keep]` the domain graph that loads the record (`current`), lays the change over it with `@std/object.port.json#merge` into the shape (`customer`, where the guard over the shape stands) and hands the result whole to the write (`kept`); `--store <store> --collection <name>` the data graph behind that write, whose `in` is the shape and whose one write is `#put` with `"record": "{{in}}"` (`stored`, `outcome`, `kept`, `repeated`, `nothingWritten`). One that decides from the record as kept whether to replace or remove it takes the read-decide-write form -- `#get` (`storedCustomer`), a switch on `has(record)` and on what it holds (`whichWrite`), one write per branch (`removed`), a switch on what that write answered (`stillThereAfterRemoved`), a record or a refusal each (`removedCustomer`, `goneBeforeRemoved`, and `noCustomer` where there was none) -- which `--store <store> --collection <name> --read-then put\|remove --branch <id>:<when>` writes with the routing in place. The ids are named from the shape (the store's, the write's, or `--type`), the write and the branch. No form writes a `#patch`, and `--read-then patch` is refused: a patch of a field an invariant reads is I007 | `domain/` or `data/` |
| `trigger` | a way in: `kind`, `settings`, `in`, `out`, `policies` (what gates it, in order, each given the credentials it needs), and `fire` -- the run node it invokes; a scheduled trigger (`@schedule/schedule.trigger-kind.json`) says `cron` (five fields, in a `timezone`) or `everyMs`, reads the tick as `request.scheduled`, and fires only while a startup step names `@schedule/scheduler.port.json#run`; a trigger whose kind declares `connection` receives messages from the connection its settings name there, one whose kind declares `delivery` | `edge/` |
| `policy` | a gate: `decide` fires a domain operation over what the guard hands (`{{request.principal}}`), `outcomes` maps each reason its graph refuses with to `deny` or `challenge`, `proves` says what is present once it allows | `edge/` |
| `invariant` | a rule that must hold: `access` (which policy gates writes to a port) or `holds` (a rule over a core shape's fields) | `domain/` |
| `resolvers` | named reads of the request (`request.params.id`, `request.headers['user-agent']`, `request.session.id`), for data graphs and bindings to bind under `reads` and read as `{{name}}`; `required` when a policy guarantees the read | `edge/` |
| `store` | what the feature keeps: a connection and collections of a core shape (or a plugin's shape), each by key, with `unique`, `refs`, `defaults`; `renamed` and `was` record what a field or the collection was called before, so a rename is read as one. A collection may be `scoped` by columns the store keeps, each filled from one read the store binds under `reads` (a `required` resolver over what the guard hands), and a `view` of a scoped collection sees every row `behind` a policy | `data/` |
| `connection` | a channel to an external system, settings read `{{secrets.*}}`; a connection whose kind declares `leases` can keep the scheduler's hold, so one instance of several fires a tick; a connection whose kind declares `delivery` is a broker, handing each message `at-least-once` (what it fires may run twice) or `at-most-once` (it may not run at all) | `connections/` |
| `scenario` | a recorded run: `wilanis fuzz` writes one per trigger per seed under `scenarios/fuzz/`, and `wilanis regress` replays every scenario under `scenarios/`; a generated scenario is regenerated, never edited. `cancelAt` pins a cancellation | `scenarios/` |

## Layers

A feature has three directories, and the directory **is** the rule -- a document's layer is where it lives,
never inferred from what references it:

```
features/<name>/
  feature.json
  edge/      triggers, policies, the shapes the world speaks, and the resolvers: what is read from the request
  domain/    the port, the core shapes, the graphs that hold business rules
  data/      the binding and the graphs that translate and reach effects
```

- **The edge** speaks the world's vocabulary. A trigger declares `in` / `out` as edge shapes and `fire`: the
  **domain port operation** it runs, with the values it passes. A trigger never names a graph -- it says what it wants done,
  and the port's binding decides how (D008, L006).
- **The domain** holds the rules. A domain graph speaks core shapes and domain ports; the only native
  operations it may run are pure. Every effect it needs, it reaches through a port (L002). It never says
  `retry` or `timeoutMs`: how long and how often a call is tried is the data layer's, on a data graph's node or
  a binding's operation (L012). A retry is refused over a pure call (G017) and over one that is not idempotent
  where it is made (G018): a POST that failed may have been applied. A domain operation that says
  `idempotent: true` is held to it under every profile: whatever the profile's binding reaches for it must be
  idempotent where it is made (B011, naming the profile, the binding and the node).
- **The data layer** translates. A data graph may name edge shapes and speaks native ports, and every
  effectful operation it reaches is listed in `feature.json → effects` (L003). It is the only layer that
  reads the request, and only through resolvers it names: `"reads": { "agent": "@f/edge/request.resolvers.json#agent" }`,
  then `{{agent}}` wherever the value is used. A resolver is a read, not an operation: nothing runs.
  A store binds a read the same way to scope a collection, and the compiler carries it to every storage
  operation over it; a graph never writes a scope.

A domain graph must earn its place: if it does nothing but forward its input to one port operation, it is
boilerplate between the trigger and the binding, and the trigger should fire that operation itself (L007).

Node types are `@wilanis/node/run.schema.json`, `@wilanis/node/switch.schema.json`, `@wilanis/node/map.schema.json`; `graph.schema.json` lists them.

Every reference is a path from the root: `@features/tasks/tasks.port.json`, or through an alias in
`project.json`: `@tasks/tasks.port.json`. Plugins are alias roots: `@std/list.port.json`,
`@http/http.port.json`. An operation is `path#operation`.

## Plugins

`project.json → plugins` lists every plugin the tree uses. `@std` (pure operations) and `@cli` (command-line
triggers) are built in. Any other plugin is an npm package named by `from`, installed in this project's
`package.json`:

```json
{ "use": "@http", "from": "@wilanis/plugin-http", "settings": { "port": 8099, "codecs": { "application/json": "@http/codecs/json.codec.json" } } }
```

`from` is a package name, never a path. `wilanis ls port`, `ls trigger-kind`, `ls connection-kind` and
`ls codec` show what the installed plugins provide; `wilanis describe <path>` lays out any of them and says
which file it is. Every document a plugin grants is a JSON file in its package (`@http/http.port.json` is
`node_modules/@wilanis/plugin-http/docs/http.port.json`; `@std` and `@cli` live under the runtime's `docs/`),
so anything the DSL names can be opened and read like a header file.

## Rules you will meet

- **One way in.** A node's `in` gives every value the operation takes. A literal is written as it is (`"method": "GET"`); a read is a template: `"{{fetched.status}}"` (another node), `"{{in.id}}"` (the graph's input), `"{{const.initial}}"`, `"{{agent}}"` (a resolver). Alone, a template takes the value and its type; inside text it interpolates: `"/tasks/{{in.id}}"`. Objects and lists are written in place with values inside. A path segment is `.name`; a key that is not an identifier is quoted in brackets: `{{fetched.headers['x-request-id']}}`.
- **A node is named for what it holds.** Its id is the word every tool uses for it -- `describe` prints it, the viewer draws it, a refusal's `at` names it, the rehearsal reports it, and the compiler builds a guard's ids from it (`customer:check`, `customer:violated`) -- so name it for what it holds once it has answered, or for the effect it performs, never for where it sits in the graph or for the operation's generic role. A `run` that answers a value is that value as a noun (`customer`, `current`, `stored`, `customers`); a `run` whose effect is the point is the effect in the past tense (`patched`, `removed`, `notified`); a `switch` is the question it asks (`wasThere`, `isGold`, `outcome`); a `refuse` is what went wrong (`noCustomer`, `repeated`, `upstreamFailed`); a `map` is the plural of what each element answers (`rows`, `repaired`). Never `asked`, `route`, `row`, `result`, `data`, `node1`: "patched answered, wasThere went to customer" tells a reader what "asked answered, route went to row" does not.
- **Static fields** (`wilanis describe` marks them) take a literal, never a read: a connection, a content type, a `type`. P001 says you gave a read where the checker needs to see the value.
- **Layers.** Triggers speak edge shapes. Domain graphs (behind triggers) speak core shapes and domain ports; the only native operations they may run are pure (`@std`). Data graphs and bindings (behind domain ports) speak native ports and may name edge shapes: they translate.
- **Effects.** Every effectful native operation a feature's data layer reaches is listed in `feature.json → effects`. L003 means add it there, deliberately.
- **A port a plugin requires is yours to bind.** Some plugins call a port they do not implement: `wilanis describe <plugin>/plugin.json` lists it under `requires`, and `wilanis describe` on the port says `required by` and what each profile binds it to. Bind it as you bind any domain port -- a binding in the `data/` of a feature of its own, `features/state/` for where the process keeps things -- or the tree is refused (B002, naming the plugin). The plugin fires it from its own code, before any policy has judged a request, so its binding declares no `reads` and reaches no `request.*` (B009), and reaches only what answers or fails, and nothing that holds or refuses on purpose -- whether it delegates to such an operation or runs a graph that ends in one (B010). `@auth` requires `@auth/state.port.json`, its sessions and challenges: bind it to `@auth/files.port.json` (one JSON file per record under `.wilanis/auth`, kept where the loader never reads -- X106 otherwise) for one process, to a store for many, and add a startup step that reads it (`@auth/state.port.json#getSession`) so an unreachable store stops the start.
- **No absence.** A field is required unless it says `required: false`. An optional read cannot feed a required input (G004). Route around it: a `switch` rule `has(x)` proves `x` present for the node it routes to.
- **Types are declared.** `@std/object.port.json#make`, `#merge`, `@std/list.port.json#first`, `#concat`, `#slice` and `@http/http.port.json#request` take a `type` / `returns` field naming the result type. The checker verifies what you gave fits it; the operation judges the value at run time.
- **The standard library** is four ports of pure operations: `@std/object.port.json` (`make` an object of a declared type from values written in place, `merge` two), `@std/text.port.json` (`fill` a template's `{name}` placeholders from `values`, `join`, `split`, `replace`), `@std/list.port.json` (`count`, `first`, `concat`, `slice`), `@std/outcome.port.json` (`refuse`: end the graph on purpose with a static `reason` and a message; a rehearsal calls it refused on purpose). `wilanis describe @std/object.port.json` lays any of them out.
- **Outcomes.** A run answers, or it fails, and a failure is a refusal or a fault. A **refusal** is the graph deciding: it says *why* in one word (`"reason": "missing"`), never how the caller is answered. The trigger says that: an http route maps each reason to a status under `settings.response.refusals` (`{ "missing": 404, "upstream": 502 }`) and answers `{ reason, message }`. T005 names a reason the route can reach but does not map; T006 a mapping nothing reaches. A **fault** is a node that breaks where no refusal is declared: it has no reason, is never mapped, and is answered the kind's one way, a 500 `{ error: 'fault', run }` for http, a line on stderr and exit 1 for the command line. A data graph's switch may `catch` a node's fault and route it to a refusal it declares: `"catch": { "fetched": "unreachable" }` sends a GET that got no answer at all to a `refuse` of `upstream`, which the route already maps to 502. The target reads nothing of the node that broke (G023), and a refusal is never caught. A fault's message reaches the report, the log and the trace, never the caller.
- **What the tree starts.** `project.json → startup` lists what runs once when `wilanis start` runs it, in order -- and nothing else runs. **The server listens because a step says so**: `{ "run": "@http/server.port.json#listen" }`. Delete that step and nothing listens; no runtime opens a port because http triggers exist. Put what the tree needs first: open a pool, declare a queue, subscribe to a topic, check that storage answers. Most steps name a **domain port operation** (`"run": "@tasks/domain/store.port.json#open"`), never a graph, so the profile's binding decides how it is met -- a fake in dev, the real connection in prod. A step's `in` is written as literals and `{{secrets.*}}` only: nothing has been received yet, so a step that reads `request.*`, or whose bound graph does, is refused (B007, B008). A step that refuses stops the start and exits nonzero, so a tree whose database is unreachable never opens its port; write `"required": false` for a step the tree can serve without, and its refusal is logged instead. An operation marked `holds` (`wilanis describe` says `holds until stopped`) starts something that outlives the run -- a listener, a watcher -- and only a startup step may name one: a graph that runs one is refused (L008). Add `@reload` to the plugins and `{ "run": "@reload/watch.port.json#watch" }` before the listener, and an edit is served without a restart. Add `@schedule` (`from: "@wilanis/plugin-schedule"`) and `{ "run": "@schedule/scheduler.port.json#run" }` beside them, and the tree's scheduled triggers fire, each at its ticks; delete the step and none does.
- **Where a step runs.** The startup list is one list, in one order, for every profile; a step that belongs to some places only names them: `{ "run": "@reload/watch.port.json#watch", "profiles": ["local"] }` watches on the laptop and nowhere else, and a step without `profiles` runs under every profile. So one process of several can be the one that schedules: a profile with the same bindings as the listening one, named by the `@schedule/scheduler.port.json#run` step and left out of the `listen` step's `profiles`. A profile named by the `@queue/worker.port.json#consume` step and left out of `listen`'s is a worker in the same way: it works the queues and opens no port, and as many of it run as the queues need, once its connection keeps the queue where every process reaches it (a table, not the in-process broker). `wilanis start` picks its profile by `--profile <name>`, else `WILANIS_PROFILE`, else the one profile marked `"default": true`, and refuses a tree that declares profiles and gives it none of the three. Before any plugin opens anything it refuses the variables the profile's reach reads and nobody set, naming each and who reads it (`missing secrets: ...; nothing is serving`): a connection only another profile reaches costs this one nothing. A connection that differs by place (a URL, a pool, an account) is another connection of the same kind named under the profile's `connections`, never an edit to a document under `features/`.
- **`request.*`** (the trigger kind's context: headers, query, params, cookies, body, flags, args... and what the guard adds: principal, session, challenge) is read in exactly three places: a trigger's `fire.in`, a policy's `decide.in`, and a `resolvers` document's `read`. Nowhere else.
- **Who may call.** A trigger with no `policies` is public. `"policies": [...]` gate it, in order, and where a policy is attached the trigger gives the guard the credentials it verifies, read from the kind's context like any input: `{ "policy": "@access/edge/signed-in.policy.json", "in": { "token": ["{{request.headers.authorization}}", "{{request.cookies.session}}"] } }` -- a list is the places a credential may sit, the first present wins; a later policy written bare reuses what an earlier one gave. The guard (`@auth`) verifies the token -- our own, issued by `@auth/token.port.json#issue` at sign-in; a `Bearer ` prefix is stripped -- and hands `request.principal` (`subject`, `realm`, `roles`), `request.session` (`id`, `attributes`), and `request.challenge` from a challenge answer (`"challenge": { "id": "{{request.flags['challenge-id']}}", "code": "{{request.flags.code}}" }`). A credential that does not verify is refused as `invalid_credential`, which the trigger maps like any reason; none at all is anonymous. Each policy then fires a domain operation with `decide.in` read from the request, and its graph allows by answering or refuses with a reason (`anonymous`, `forbidden`, `otp`) that the policy's `outcomes` calls a `deny` or a `challenge` and the trigger maps to an answer (T005). A challenge opens through the guard and the caller is told its id and how to answer it, in the kind's own words; the graph never sees a code. Never validate a credential in a graph: `@auth/identity.port.json#verify` judges a password against a directory connection, the guard judges tokens and codes. `wilanis describe @auth/plugin.json` lists the credentials the guard takes and what each yields.
- **The rule behind the gates.** Attaching the same policy to five triggers says it five times and says nothing about the sixth. An `invariant` (in `domain/`) states the rule once and the checker holds the whole tree to it: `"access": { "over": ["@customers/domain/customer.port.json#register", ...], "requires": { "policy": "@access/edge/can-register.policy.json" } }` -- every way in that reaches one of those operations attaches that policy. Write `"requires": { "proves": ["request.principal"] }` instead to name what must be established rather than which policy establishes it; any attached policy whose `proves` lists that path or one above it qualifies, and a public trigger does not. Reaching is transitive: a trigger firing `#import`, whose graph calls `#record` for every row, reaches `#record` too, so a domain graph cannot route around the rule by calling the operation itself. An invariant never names a role -- the gate standing is its business, what the gate decides is the policy's. Write one the moment a gate is a rule rather than a habit: it is what stops a route added later from checking clean while it writes in public. I003 says no trigger reaches anything it covers, so it gates nothing; an invariant an include shipped is exempt, since a library states what it requires of whoever reaches its ports.
- **Reading an I001.** `trigger reaches @features/customers/domain/customer.port.json#remove, which 'Writes are for registrars' (@features/customers/domain/writes-are-for-registrars.invariant.json) gates with @access/edge/can-register.policy.json, but attaches no such policy` -- a way in you wrote is not gated the way a rule of this tree says it must be. It names the operation reached, and `reached through <op>` when your trigger fired something else that calls it. Two fixes, and the hint gives both: attach the policy under `policies` (giving the guard its credentials where no earlier policy did), or take the operation out of the invariant's `over` -- the second only when the rule was wrong, never to quiet the refusal. The `proves` form reads `requires "request.principal" proved, but attaches no policy that proves it`, and is met by attaching any policy that proves it.
- **A field invariant guards what a graph answers, not what a store keeps.** `"holds": { "on": "@customers/domain/Customer.shape.json", "when": "len(name) > 0 && len(email) > 0 && (tier != 'gold' || has(note))" }` states a rule over a core shape's fields once, and the compiler judges every place a value of that shape is made or taken: proved where the routing, the literals or a read of another site already established it, and otherwise guarded by a `switch` it lowers for you, refusing with the reserved reason `invariant`. The guard stands where the value is made -- so a graph that writes and *then* answers has already written when the guard fires. A `#patch` that moves a customer to `gold` with no note commits, the answer is refused, and the row stays broken: every later read of it refuses too. Make the decision before the effect. The form that lasts: load the record, lay the change over it with `@std/object.port.json#merge` (`"base": "{{current}}", "over": "{{in}}", "type": <the shape>`) in a domain graph, and hand the result to an operation whose data graph `#put`s it whole -- the merge is where the value is made, so the guard fires before anything is written; `wilanis new graph <path> --port <port>` scaffolds the domain half and `--store <store> --collection <name>` the writing half. A `switch` in front of a `#patch` works only if it judges the record as the change will leave it: a switch over `{ "record": "{{storedCustomer.record}}" }` sees the row before the change, so widen its `in` with the incoming fields and write the `when` over both (`in.tier != 'gold' || has(in.note) || has(record.note)`); a switch over the stored row alone lets the bad patch through. RFC 0035 will refuse a `#patch` whose `changes` name a field an invariant reads, so prefer the merge. Or mark the graph `"atomic": true`, so the refusal ends the transaction and the write rolls back with it.
- **Including a tree.** `project.json → includes: [{ "from": "@wilanis/access", "features": ["access"] }]` loads that package's features as if they sat here: `dependsOn` it, name its exports, attach its policies, and bind the ports it leaves unbound (`wilanis check` says which, B002) in a feature of your own. Its aliases come along; its connections, plugins and settings do not: configure the plugins it uses (D010 names one you forgot) with the settings its README gives. `wilanis describe <path>` says `included from` when a document is another tree's; edit it there.
- **Sessions.** `@auth` settings name the session shape (`"session": "@access/domain/Session.shape.json"`); `@auth/session.port.json#get`, `#set`, `#remove`, `#end` read and write its attributes from a data graph, keyed by `{{sid}}` from a resolver reading `request.session.id`. Declare that resolver `required` and give the gating policy `"proves": ["request.principal", "request.session"]`, so the read is present by construction (A006). X103 refuses a write of an attribute the shape does not declare, and X105 a write of one some store scopes a collection by: a scope is what the sign-in graph gave `@auth/token.port.json#issue`, and nothing writes it again. `wilanis describe <the session shape>` lists who writes what.
- **Membership.** `'registrar' in principal.roles` is true when the list holds the value. A read through a value that may be missing is refused in a rule unless a `has()` on the left of the same `&&` proved it: `has(principal) && principal.realm == 'employee'`.
- **`http.request`** executes and reports `status`, `headers`, `body`. It does not decide what a 404 means; a `switch` on `status` does. `returns` types the body of a 2xx only, so an error body reaches the switch. How many requests may hit one API at once is the connection's business, not the graph's: `"throttle": { "concurrency": 4, "perSecond": 10 }` on the connection paces every request made against it, a `map` fanning out one per element included.
- **A graph's `in`** is usually a shape, read as `{{in.field}}`. It may be any type instead -- `"in": "string[]"` -- read whole as `{{in}}`; a binding meets such a graph with an operation that accepts exactly one field, and that field is what the graph receives (B005 otherwise).
- **Many at once.** A `map` node runs one operation per element of `over`, all at once, and settles only when every element has; its result is the list of theirs, in order. Bind the element to the operation's inputs (`"bind": { "id": "" }` hands the whole element as `id`) or let it arrive as `item`. One element that fails fails the node, once the others are done.
- **Files are blobs.** A `blob` field or `in`/`out` is a stored file, carried as a handle (`id`, `contentType`, `size`, `filename`); the bytes never enter a graph. A route uploads one through a content type the `@http` codecs table maps to `@http/codecs/blob.codec.json` (`"text/csv": ...`), with `settings.body: "blob"` and `fire.in` reading `{{request.body}}`; it downloads one by declaring `out: "blob"` and a `produces` mapped to that codec. A data graph reads the file with `@blob/csv.port.json#parse` (rows of a declared `type`) or `@blob/text.port.json#read`, and makes one with `#write`; these are effects, listed in `feature.json → effects`. On the command line, `wilanis run --file path` hands a file as `request.file` and `--out path` receives a blob answer.
- **Records are a store's.** A `store` (in `data/`) names a connection and its collections: each a core shape, keyed by one of its fields, and that is the one place the record type is written -- a call names the store and the collection and repeats no shape. A data graph reads and writes through `@storage/store.port.json`: `#get` one by key, `#find` what a filter matches (ordered, paged), `#count`, `#put` one whole record, `#patch` some fields of one, `#remove`, and `#newKey` for a key no record has. Each is an effect, so it lives in a data graph and is listed in `feature.json → effects`. **Nothing that could be expected is a failure.** A key nothing is kept under answers `record` absent, not an error, so a graph routes on `has(record)` with a `switch`; a `#put` with `"replace": false` over a key that exists answers `conflict`; a `unique` the store declares and a write repeats answers `violated`, and a `#remove` of a record another collection still references answers `removed: false` and `referencedBy`. Route on the flag -- a failure is for the unforeseen, and a constraint the store itself declares is the opposite of that. Which engine keeps the records is the connection's kind: `@storage-memory` for as long as the process, `@storage-postgres` in a database, with no other change to the tree. Prepare them from a startup step (`@storage/storage.port.json#ensure` behind a domain port), never from a graph.
- **Content types** are explicit: `consumes` / `produces` on triggers and on `http.request` must be in the `@http` codecs table in `project.json`.
- **Reconvergence** happens only at `out.from`: a list of candidates, each behind a switch, the first that settled answers.
- **A switch chooses who answers, not who runs.** A graph is dataflow: a node runs when every input it reads is ready, whatever any switch chose, and the only node a switch holds back is the one its rule names as `to`. So an effect only one branch needs must be that switch's `to`, or it runs on every branch -- two `#patch` nodes written beside the switch meant to choose between them both write on every call, and the switch decides nothing but which answer is forwarded. Branches are joined at `out.from`, one candidate per branch, never with `||` between two nodes' answers in one template. When you need a graph shape, do not invent it: find the nearest graph in the tree and copy it (`wilanis ls graph`, then `wilanis describe <path>`); the skill `.claude/skills/wilanis-graphs/SKILL.md` has the read-decide-write shape over a store written out.
